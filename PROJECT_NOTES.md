# 1. Идея проекта

BLACKBOX — локальная платформа для исследования киберинцидентов и реконструкции атак на основе собранных событий.

Главная идея:

Система получает набор разрозненных событий, анализирует их, устанавливает связи и пытается восстановить последовательность действий, которые привели к инциденту.

Пример:

1. Запущен Bash.
2. Bash запускает Python.
3. Python запускает curl.
4. Зафиксировано сетевое соединение.
5. Detection Engine обнаруживает подозрительную цепочку.
6. Correlation Engine связывает события.
7. Timeline Builder строит временную шкалу.
8. Investigator объясняет, что произошло.

В перспективе BLACKBOX должен уметь проводить расследование без предварительного знания сценария. После расследования можно будет сравнить результат системы с реальной последовательностью действий в тестовом сценарии.

# 2. Основная концепция

BLACKBOX разделён на несколько независимых компонентов.

## 2.1 Scenario Simulator

Назначение: генерация тестовых сценариев.

Симулятор создаёт события, которые имитируют поведение процессов, сетевые соединения и другие действия.

Он нужен для разработки и тестирования остальных компонентов без необходимости постоянно запускать настоящие атаки.

Текущая реализация:
- Сценарии хранятся в JSON.
- Симулятор читает сценарий.
- События отправляются в локальный API.
- Каждое событие помечается как synthetic.
- Используется идентификатор сценария.

Текущий тестовый сценарий: BB-001.

## 2.2 Event Collector

Назначение: приём событий.

Collector должен принимать события от разных источников и передавать их в общую систему обработки.

Планируемые источники:
- Scenario Simulator.
- Linux audit/journald.
- Windows Sysmon (после получения доступа к Victus).
- Другие лабораторные источники.

Важно: все источники должны использовать единый внутренний формат событий.

## 2.3 Event Normalization

Назначение: преобразование событий в единый формат.

Разные источники могут по-разному называть одинаковые поля.

Например:
- pid;
- process_id;
- ProcessId.

Normalization должен приводить их к общей структуре.

Планируемые поля:
- event_id;
- timestamp;
- event_type;
- source;
- hostname;
- process_name;
- pid;
- parent_pid;
- command_line;
- source_ip;
- destination_ip;
- destination_port;
- protocol;
- severity;
- raw_data.

Нужно сохранить исходное событие, чтобы не терять доказательную информацию.

## 2.4 Detection Engine

Назначение: обнаружение подозрительных событий.

Будет использовать набор правил, похожих по концепции на Sigma.

Пример будущего правила:

```yaml
title: Suspicious Process Chain
id: BB-RULE-001
description: Detect a suspicious process chain
logsource:
  product: linux
detection:
  selection:
    event_type: process_created
    process_name: curl
  condition: selection
level: medium
```

Detection Engine должен:
- Загружать правила.
- Проверять события.
- Создавать alerts.
- Сохранять причину срабатывания.
- Передавать результаты в Correlation Engine.

## 2.5 Correlation Engine

Назначение: установление связей между событиями.

Основные механизмы:
- PID и Parent PID.
- Временные метки.
- Имена процессов.
- Сетевые атрибуты.
- Общий идентификатор сценария или хоста.

Пример:

```text
bash (PID 1000)
  └── python3 (PID 1100)
        └── curl (PID 1200)
              └── network connection
```

Результатом должна быть связанная цепочка событий, а не просто список записей.

## 2.6 MITRE ATT&CK Mapping

Назначение: сопоставление обнаруженных действий с техникой MITRE ATT&CK.

Система должна определять, какие действия могут соответствовать известным техникам.

Важно: сопоставление должно иметь обоснование и уровень уверенности. Нельзя автоматически считать любое подозрительное событие подтверждением конкретной техники.

## 2.7 Timeline Builder

Назначение: построение временной шкалы.

Timeline должен показывать:
- Время события.
- Тип события.
- Процесс.
- Связанные процессы.
- Сработавшие правила.
- Уровень серьёзности.

## 2.8 Evidence Graph

Назначение: визуализация связей.

Планируется использовать Cytoscape.js.

Узлы:
- Процессы.
- События.
- IP-адреса.
- Alerts.
- Файлы.

Рёбра:
- parent-child;
- created;
- connected_to;
- triggered;
- correlated_with.

## 2.9 AI Investigator

Назначение: помощь в расследовании.

Планируется локальная модель через Ollama.

AI Investigator должен:
- Объяснять цепочки событий.
- Формировать гипотезы.
- Объяснять срабатывания правил.
- Выделять недостающие доказательства.
- Формировать отчёт расследования.

AI не должен придумывать доказательства. Все выводы должны ссылаться на конкретные события.

Этот модуль будет реализовываться после появления устойчивой структуры данных и механизма корреляции.

## 2.10 Web Dashboard

Назначение: единый интерфейс платформы.

Планируемый стек:
- React.
- TypeScript.
- Cytoscape.js.
- FastAPI backend.

Основные страницы:
- Dashboard.
- Events.
- Alerts.
- Incidents.
- Timeline.
- Evidence Graph.
- Investigation Report.
- Settings.

2. Сначала проверяем архитектуру, затем пишем код.

  обоснование. HTTP→процесс привязывается по родителю (веб-сервер) и по

- Эндпоинт `GET /incidents/{scenario}/graph`.

## Day 4 (частично) — Web Dashboard

- Граф инцидента на Cytoscape (`GET /ui`), Cytoscape вшит локально.
- Узлы по типу (форма + цвет), связи по типу (цвет + стиль), режим

## Day 6 — Reconstruction Engine + Investigation Console + i18n

- **Фикс времени Tetragon (баг корреляции).** Часы Tetragon уезжают после
  suspend/resume ноутбука (он реконструирует настенное время из монотонных
  часов + смещение, снятое при старте), процессы оказывались на ~51 минуту
  «позже» HTTP-логов и вылетали из окна корреляции → ноль связей
  `spawned_by`. Коллектор теперь штампует событие временем получения на
  часах хоста (тот же источник времени, что у лога Apache), а исходный
  `start_time` Tetragon хранит в `data.source_timestamp` как доказательство.
- **Reconstruction Engine** (`backend/reconstruction.py`,
  `GET /incidents/{case}/reconstruction`). Набор детекторов превращает
  события + граф в упорядоченную историю атаки: этап = тактика + техника
  MITRE + обоснование техники + уровень уверенности + ссылки на конкретные
  события (chain of custody). Ничего не выдумывает: нет сигнала — нет этапа.
  На machine1: `.git`-утечка (T1595.003), SQLi (T1190), загрузка вебшелла
  (T1505.003), RCE (T1059), privesc (T1548); overall confidence = high.
- **Трёхъязычность на бэкенде.** `title`/`tactic`/`summary`/`technique_reason`
  отдаются как `{en, ru, kz}` — один источник правды, счётчики верны в
  каждом языке. Коды и названия техник MITRE остаются каноничными (EN).
- **Investigation Console** (`/ui`, переписан). Три колонки: слева история
  атаки (таймлайн этапов), в центре граф-доказательство (Cytoscape), справа
  панель доказательств. Клик по этапу подсвечивает его узлы и показывает
  backing events. Переключатель языка RU/EN/KZ, сворачиваемые боковые
  колонки-шторки — всё сохраняется в localStorage. URL-override:
  `?lang=kz&hide=left,right#stage=<key>`.
- **Офлайн-демо.** Снятый инцидент → `fixtures/incident_bb_m1.jsonl` +
  `scripts/replay.py`. На финале демо работает без Tetragon и без уязвимых
  машин: `replay.py` заливает фикстуру в API и граф/история воспроизводятся
  (169 событий, проверено).
- Тесты: 35, все проходят (+10 к reconstruction, +правки collector-теста).

## Day 7 — Timeline + целостность доказательств (хеш-цепочка)

- **Evidence integrity** (`backend/integrity.py`, `GET /integrity`).
  Tamper-evident хеш-цепочка по всем событиям в порядке приёма:
  `content_hash = sha256(каноническое событие)`,
  `chain_hash = sha256(prev_chain_hash + content_hash)`. Правка события
  меняет его `content_hash`; удаление/перестановка рвут `prev_hash`
  следующего — верификация падает и указывает на первую испорченную запись.
  `head` (последний `chain_hash`) — единственное значение, фиксирующее всю
  историю (его и надо «засвидетельствовать» вовне). Хеши считаются на
  ingestion (`POST /events`), колонки `content_hash/prev_hash/chain_hash`
  в `events`.
- **Timeline** (`GET /incidents/{case}/timeline`). События в хронологии с
  типом, меткой, принадлежностью этапам реконструкции и коротким
  `chain_hash`.
- **UI:** переключатель «Граф / Таймлайн» в центре; строки таймлайна
  тегированы номерами этапов и подсвечиваются при выборе этапа; бейдж
  целостности в шапке («подтверждена · N · head …», красный при нарушении).
  Переводы RU/EN/KZ, URL-override `?view=timeline`.
- Тесты: 43, все проходят (+8 integrity).

## Day 8 — Target Manager (загрузка сайтов-целей)

- **`backend/targets.py` + эндпоинты `/targets`, `/sensor`.** Цель =
  контейнеризованный сайт. Источник: готовый Docker-образ или папка с
  Dockerfile (BLACKBOX собирает). Жизненный цикл add/start/stop/delete:
  `start` собирает образ (если build), запускает контейнер **всегда на
  `127.0.0.1`** (цель уязвима — наружу не публикуем), авто-подключает
  HTTP-коллектор, а при включённом сенсоре — и Tetragon-коллектор. Каждая
  цель → своё дело `TGT-<slug>`. Контейнер цели **непривилегированный**;
  единственная привилегированная часть — сенсор Tetragon, управляется
  отдельно (`/sensor/start|stop`, грузит tcp-connect политику).
- **GUI `/ui/targets.html`** (RU/EN/KZ): панель движка захвата (вкл/выкл),
  форма загрузки цели (образ / Dockerfile, порт), список целей со
  статусом и кнопками Start/Stop/Delete + «Открыть дело». Ссылка из
  консоли («Цели ▸») и обратно; консоль открывает дело цели по
  `?case=<scenario>`.
- Проверено сквозняком: загрузил `ice-public-portal` образом → Start
  (поднялся на 127.0.0.1:8100, HTTP-коллектор сам подключился) → атака
  `solve.py` → дело `TGT-ice-portal`, реконструкция 3 этапа из HTTP-only
  (recon/SQLi/upload; RCE/privesc появляются при включённом сенсоре) →
  Stop убрал контейнер и коллекторы. `/sensor/start|stop` поднимает и

### Схема с двумя ноутами (атакующий + лаборатория)
Tetragon и коллекторы живут на ноуте-лаборатории (там крутятся контейнеры).
Чтобы атаковать с другого ноута, цель должна быть видна по сети — поэтому
нужна **выделенная изолированная сеть** между ноутами (кабель/свитч, статика,
без шлюза), отрезанная от Wi-Fi и интернета: (1) снаружи не найдут уязвимую
цель, (2) захваченная цель не достучится наружу (эксфил/пивот/атака третьих
лиц), (3) промах AI-агента остаётся в песочнице. На одном ноуте `127.0.0.1`
даёт эту изоляцию бесплатно.

## Открытые вопросы / нюансы

- HTTP→процесс для коротких команд (напр. `id`, проба < 4 символов)
  привязывается по времени, а не по содержимому; т.к. атака укладывается в
  1 сек (логи Apache с разрешением 1 сек), в доказательства RCE может
  попасть посторонний запрос. Связь «carried the command» (privesc) —
  точная. Зафиксировано как ограничение точности.
- Tetragon требует привилегированный контейнер (eBPF) и имеет перекос
  настенных часов после suspend — поэтому время берём на стороне коллектора.
- Уязвимые машины поднимать только на `127.0.0.1`.

**Главная цель BLACKBOX:** не просто обнаружить подозрительное событие, а объяснить, что произошло, в какой последовательности, какие доказательства это подтверждают и насколько достоверна реконструкция.
